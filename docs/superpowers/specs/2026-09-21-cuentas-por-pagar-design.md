# Cuentas por Pagar — Design

## Contexto

Hoy el sistema solo registra lo que la empresa debe *cobrar* (`cl.slimerp.tesoreria.CuentaPorCobrar`, generada al confirmar una `Venta` a crédito, pagada vía `TransaccionPago`). No existe ningún registro de lo que la empresa debe *pagar*: `Compras` (`cl.slimerp.compras`) mueve stock y calcula un `total`, pero no genera deuda ni pasa por Tesorería. Tampoco existe un módulo de Gastos (arriendo, servicios, sueldos, etc.) — solo había una spec sin implementar (`docs/superpowers/specs/2026-09-11-modulo-gastos-design.md`) que proponía sincronizar gastos como líneas de solo lectura en Flujo de Caja, sin manejo de deuda.

El usuario necesita **Cuentas por Pagar**: el espejo de Cuentas por Cobrar, cubriendo dos orígenes — documentos de compra y gastos recurrentes — con saldo pendiente, pagos parciales y estado, igual que ya funciona para las ventas.

## Decisiones validadas con el usuario

1. **Alcance**: Cuentas por Pagar es un espejo completo de Cuentas por Cobrar (deuda, saldo pendiente, pagos parciales, estado) para **ambas fuentes**: documentos de compra y gastos recurrentes.
2. **Origen Compras**: no se agrega forma de pago (contado/crédito) a `Compra`. **Toda compra registrada genera automáticamente una `CuentaPorPagar`**, sin excepción.
3. **Origen Gastos**: se construye el módulo de Gastos completo (`cl.slimerp.gastos`: categoría de gasto, gasto puntual, gasto recurrente con job diario de generación, pantalla propia Tesorería > Gastos), según la spec 2026-09-11 — con el cambio de que cada `Gasto` creado (manual o generado por el job) ahora genera automáticamente su `CuentaPorPagar`.
4. **Modelo de datos**: una sola tabla `cuenta_por_pagar` con origen nullable (`compra_id`/`gasto_id`, exactamente uno seteado vía `CHECK`) y un solo `transaccion_pago_compra` para los pagos — en vez de tablas separadas por origen o un origen polimórfico sin FK real. Se prefirió por reutilizar el patrón ya probado de `CuentaPorCobrar`/`TransaccionPago` y mantener integridad referencial real en base de datos.
5. **Permisos**: sin permisos nuevos. Gastos y Cuentas por Pagar quedan gateados por los permisos ya existentes `TESORERIA_VER`/`TESORERIA_EDITAR`/`TESORERIA_ANULAR`.
6. **Sincronización a Flujo de Caja**: se sincronizan los **pagos confirmados** (`transaccion_pago_compra` con `estado=CONFIRMADA`), no la deuda generada — simétrico a como Cobros sincroniza `TransaccionPago` confirmados y no las `Venta`. Una `CuentaPorPagar` sin pagos no aparece en Flujo de Caja.
7. **Restricción global de git**: ningún paso de este trabajo —ni al escribir esta spec, ni durante la implementación, ni ningún subagente que se despache para ejecutarla— debe correr comandos git que muten el repositorio (`add`, `commit`, `push`, `merge`, `reset`, creación de ramas, etc.). Comandos de solo lectura (`status`, `diff`, `log`, `show`) sí están permitidos para inspección. El commit se hace únicamente cuando el usuario lo pida explícitamente en el momento.

## Arquitectura

```
Backend (nuevo): cl.slimerp.gastos
  categoria_gasto ← CRUD simple (igual que catalogo.Categoria)
  gasto_recurrente ← plantilla de gasto periódico
  gasto ← registro real (puntual o generado desde gasto_recurrente)
       ↑ genera automáticamente su CuentaPorPagar
  GastoRecurrenteGeneratorJob (@Scheduled, diario) crea filas `gasto`

Backend (extendido): cl.slimerp.tesoreria
  cuenta_por_pagar ← generada por CompraService.crear() (toda compra)
                      y por GastoService.crear() (todo gasto)
       ↑
  transaccion_pago_compra ← pagos parciales/totales contra una cuenta_por_pagar

Frontend (nuevo): frontend/src/app/features/gastos/
  Tesorería > Gastos → CRUD de gastos + categorías + recurrentes

Frontend (nuevo): frontend/src/app/features/cuentas-por-pagar/
  Tesorería > Cuentas por Pagar → mirror de features/tesoreria/ (Cuentas por Cobrar)

Frontend (flujo-caja, extendido): PagosCompraSyncService
  pagina TransaccionPagoCompraService.buscar({estado:'CONFIRMADA'}) → SyncedExpense[] → projection.ts
  (mismo patrón que CobrosSyncService / SyncedIncome)
```

## 1. Backend — modelo de datos

### 1a. `cl.slimerp.gastos` — Migración `V29__gastos.sql`

Todas las tablas `tenant_id BIGINT NOT NULL REFERENCES tenant(id)`, `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, montos `NUMERIC(14,2)`.

```sql
CREATE TABLE categoria_gasto (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    nombre VARCHAR(100) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT uq_categoria_gasto_tenant_nombre UNIQUE (tenant_id, nombre)
);

CREATE TABLE gasto_recurrente (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    categoria_gasto_id BIGINT NOT NULL REFERENCES categoria_gasto(id),
    monto NUMERIC(14,2) NOT NULL,
    descripcion VARCHAR(255) NOT NULL,
    dia_mes SMALLINT NOT NULL CHECK (dia_mes BETWEEN 1 AND 28),
    fecha_inicio DATE NOT NULL,
    fecha_fin DATE,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now()
);

CREATE TABLE gasto (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    categoria_gasto_id BIGINT NOT NULL REFERENCES categoria_gasto(id),
    gasto_recurrente_id BIGINT REFERENCES gasto_recurrente(id),
    monto NUMERIC(14,2) NOT NULL,
    descripcion VARCHAR(255) NOT NULL,
    fecha DATE NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX idx_gasto_tenant_fecha ON gasto (tenant_id, fecha);
CREATE INDEX idx_gasto_recurrente_origen ON gasto (gasto_recurrente_id);
```

`dia_mes` se limita a 1-28 para que todo mes (incluido febrero) tenga ese día — evita reglas especiales de fin de mes.

Java, package `cl.slimerp.gastos`: entidades `CategoriaGasto`, `GastoRecurrente`, `Gasto` (mismo estilo Lombok `@Entity`/`@Getter`/`@Setter`/`@Builder` que `Categoria`/`Compra`).

### 1b. `cl.slimerp.tesoreria` — Migración `V30__cuentas_por_pagar.sql`

```sql
CREATE TABLE cuenta_por_pagar (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    compra_id BIGINT REFERENCES compra(id),
    gasto_id BIGINT REFERENCES gasto(id),
    descripcion VARCHAR(255) NOT NULL,
    fecha_generacion TIMESTAMP NOT NULL DEFAULT now(),
    monto_total NUMERIC(14,2) NOT NULL,
    monto_pagado NUMERIC(14,2) NOT NULL DEFAULT 0,
    saldo_pendiente NUMERIC(14,2) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'DEUDA',
    fecha_ultimo_pago TIMESTAMP,
    observaciones VARCHAR(500),
    usuario_anulo_id BIGINT,
    fecha_anulacion TIMESTAMP,
    motivo_anulacion VARCHAR(500),
    CONSTRAINT chk_cxp_un_origen CHECK (
        (compra_id IS NOT NULL AND gasto_id IS NULL) OR
        (compra_id IS NULL AND gasto_id IS NOT NULL)
    )
);

CREATE TABLE transaccion_pago_compra (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    cuenta_por_pagar_id BIGINT NOT NULL REFERENCES cuenta_por_pagar(id),
    compra_id BIGINT,
    gasto_id BIGINT,
    fecha TIMESTAMP NOT NULL DEFAULT now(),
    monto NUMERIC(14,2) NOT NULL,
    medio_pago VARCHAR(20) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'CONFIRMADA',
    usuario_id BIGINT,
    observaciones VARCHAR(500),
    transferencia_banco_origen VARCHAR(100),
    transferencia_banco_destino VARCHAR(100),
    transferencia_numero_operacion VARCHAR(100),
    transferencia_fecha DATE,
    tarjeta_entidad VARCHAR(100),
    tarjeta_tipo VARCHAR(50),
    tarjeta_numero_operacion VARCHAR(100),
    tarjeta_fecha DATE,
    cheque_banco VARCHAR(100),
    cheque_numero VARCHAR(50),
    cheque_fecha_emision DATE,
    cheque_fecha_pago DATE,
    usuario_anulo_id BIGINT,
    fecha_anulacion TIMESTAMP,
    motivo_anulacion VARCHAR(500)
);

CREATE INDEX idx_cxp_tenant_estado ON cuenta_por_pagar (tenant_id, estado);
CREATE INDEX idx_pago_compra_cxp ON transaccion_pago_compra (cuenta_por_pagar_id);
```

`descripcion` se calcula una única vez al crear la cuenta (ej. `"Compra C-123 — Proveedor X"` o `"Arriendo — oficina"`) y no se recalcula si cambia el proveedor/categoría después — mismo criterio que `synced-income.ts` hoy en Flujo de Caja.

`compra_id`/`gasto_id` en `transaccion_pago_compra` son denormalizados desde la cuenta (igual que `venta_id`/`cliente_id` en `transaccion_pago`), para filtrar el historial sin join; nunca ambos a la vez, siguiendo el mismo origen que su `cuenta_por_pagar`.

Java: entidades `CuentaPorPagar`, `TransaccionPagoCompra` en `cl.slimerp.tesoreria`, junto a `CuentaPorCobrar`/`TransaccionPago` — mismo dominio.

Estados (`EstadoCuentaPorPagar`): `DEUDA`, `PARCIAL`, `PAGADA`, `ANULADA` — mismo enum que `EstadoCuentaPorCobrar`.

## 2. Backend — servicios y endpoints

### `cl.slimerp.gastos`
- `CategoriaGastoService`/`Controller`/`Repository` — calco de `CategoriaService`/`Controller`/`Repository`. `GET/POST/PUT /api/gastos/categorias`.
- `GastoRecurrenteService`/`Controller`/`Repository` — CRUD de plantillas. Desactivar una plantilla no borra ni afecta los `Gasto` ya generados. `GET/POST/PUT /api/gastos/recurrentes`.
- `GastoService`/`Controller`/`Repository` — CRUD de gastos puntuales + listado paginado con filtros (rango de fecha, categoría). `GET/POST/PUT/DELETE /api/gastos`.
  - `crear()` valida que `categoriaGastoId` pertenezca al tenant y esté activa.
  - Al final de `crear()` (tanto alta manual como la generada por el job), llama a `cuentaPorPagarService.crearParaGasto(gasto)` — mismo punto donde `VentaService` llama a `cuentaPorCobrarService.crearParaVenta(venta)`.
  - Editar/eliminar un `Gasto` generado por una recurrencia es igual a uno puntual — son instancias independientes una vez creadas.

Todos los servicios usan `TenantContext.getTenantId()`, igual que `CompraService`/`CategoriaService`.

### Job de generación automática
`GastoRecurrenteGeneratorJob`, `@Scheduled(cron = "0 0 3 * * *")` (diario, 03:00). No existe `@Scheduled` en el proyecto hoy: se agrega `@EnableScheduling` en `SlimErpApplication`.

Por cada tenant y cada `gasto_recurrente` activo cuyo `dia_mes` sea hoy (y `fecha_inicio <= hoy` y (`fecha_fin` es null o `>= hoy`)):
- Si ya existe un `gasto` con ese `gasto_recurrente_id` cuya `fecha` caiga en el mes actual → no hace nada (idempotencia, cubre reinicios/reintentos del job).
- Si no existe → llama a `GastoService.crear()` con `fecha = hoy`, `monto`/`descripcion`/`categoria_gasto_id` copiados de la plantilla, `gasto_recurrente_id` seteado — lo que también dispara la creación de su `CuentaPorPagar`.

### `cl.slimerp.tesoreria` (extendido)
- **`CuentaPorPagarService`**:
  - `crearParaCompra(Compra compra)` — llamado desde `CompraService.crear()` al final, sin condición de forma de pago.
  - `crearParaGasto(Gasto gasto)` — llamado desde `GastoService.crear()`.
  - `buscar(filtros)` — paginado, filtros: `origen` (COMPRA/GASTO), `proveedorId` (solo si origen=COMPRA), `categoriaGastoId` (solo si origen=GASTO), `estado`, `busqueda` (sobre `descripcion`), rango de fecha. Mismo patrón que `CuentaPorCobrarService.buscar()`.
  - `obtener(id)`.
  - `resumen()` → `ResumenCuentasPorPagar(totalPorPagar, totalPagado, saldoPendiente, cuentasEnDeuda, cuentasParciales, cuentasPagadas)` — calco de `ResumenTesoreria`.
- **`CuentaPorPagarController`**: `GET /api/tesoreria/cuentas-por-pagar`, `GET /api/tesoreria/cuentas-por-pagar/{id}`, `GET /api/tesoreria/cuentas-por-pagar/resumen`.
- **`TransaccionPagoCompraService`**:
  - `registrarPago(cuentaPorPagarId, request)` — valida que la cuenta no esté `ANULADA` ni ya `PAGADA`, que `monto <= saldoPendiente`; actualiza `montoPagado`/`saldoPendiente`/`estado` (`PARCIAL` si queda saldo, `PAGADA` si llega a cero) y `fechaUltimoPago`. Mismo patrón que `TransaccionPagoService.registrarPago()`.
  - `buscar(filtros)` — historial paginado (mismo shape que `FiltrosHistorialPago`), incluye en la respuesta `cuentaPorPagarDescripcion` (join de solo lectura al armar el DTO) para que el frontend no necesite pedir la cuenta aparte.
  - `anular(id, motivo)` — revierte el pago del saldo de la cuenta (resta `monto` de `montoPagado`, recalcula `saldoPendiente`/`estado`) y marca el pago `ANULADA`.
- **`TransaccionPagoCompraController`**: `POST /api/tesoreria/cuentas-por-pagar/{id}/pagos`, `GET /api/tesoreria/pagos-compra` (historial con filtros, incluye `estado=CONFIRMADA` para el consumo de Flujo de Caja), `POST /api/tesoreria/pagos-compra/{id}/anular`.

Todos los servicios usan `TenantContext.getTenantId()`.

## 4. Sincronización a Flujo de Caja

Simétrico a Cobros: Flujo de Caja refleja pagos confirmados, no deuda generada.

- `frontend/.../flujo-caja/core/pagos-compra-sync.service.ts` (nuevo, reemplaza el `gastos-sync.service.ts` que proponía la spec 2026-09-11): pagina `TransaccionPagoCompraService.buscar({estado: 'CONFIRMADA', pagina, tamano: 200})` hasta traer todo — mismo patrón que `CobrosSyncService.traerTodosLosConfirmados()`.
- `frontend/.../flujo-caja/core/synced-expense.ts` (nuevo):
  ```ts
  export interface SyncedExpense {
    id: string;                 // `pago-compra-${pago.id}`
    month: MonthKey;            // pago.fecha.slice(0,7)
    description: string;        // `Pago ${pago.cuentaPorPagarDescripcion}`
    amount: number;
    cuentaPorPagarId: number;   // para el link "Ver cuenta por pagar"
  }
  ```
- `core/projection.ts`: `Line['source']` ya soporta `'synced'` (de la spec de Cobros). `projectMonth`/`projectMonths`/`projectThrough`/`projectYear` ganan `syncedExpenses: readonly SyncedExpense[] = []`, con un loop análogo al de `syncedIncomes` pero `kind: 'expense'`. Los gastos sincronizados se categorizan a una categoría fija nueva (ej. `cat-gastos-pagados`, nombre exacto a definir al implementar) — igual que los cobros usan `CATEGORIA_VENTAS_ID`. `Line` gana `cuentaPorPagarId?: number` opcional (paralelo a `cuentaPorCobrarId`).
- `core/cashflow.store.ts`: nueva señal `_syncedExpenses`, nuevo método `syncPagosCompra()` (mismo manejo de `syncing`/`syncError`/403 que `syncCobros()`), llamado también en el constructor. `projection` computed pasa `syncedIncomes` **y** `syncedExpenses` a `projectYear`.
- `month/month-detail.html`: la rama que hoy distingue `source: 'synced'` (ingresos) se extiende a gastos sincronizados — mismo ícono `sync`/tooltip, sin editar/eliminar, con link "Ver cuenta por pagar" hacia `/cuentas-por-pagar?id={{ line.cuentaPorPagarId }}`.

**Nota**: una `CuentaPorPagar` sin pagos (estado `DEUDA`) no aparece en Flujo de Caja — es deuda contraída, no gasto de caja todavía. Una vista de "vencimientos próximos" queda fuera de alcance (ver más abajo).

## Fuera de alcance

- Proyección de vencimientos futuros (lo que se va a deber, no solo lo pagado) en Flujo de Caja — solo se sincronizan pagos confirmados, igual que Cobros.
- Compras no incorpora forma de pago (contado/crédito); toda compra genera `CuentaPorPagar` sin excepción.
- No hay deduplicación entre una cuenta por pagar sincronizada y un ítem manual (`OneOffItem`/`RecurringItem`) ya cargado a mano en Flujo de Caja para el mismo concepto — mismo comportamiento que ya existe con Cobros.
- No se modifica `CuentaPorCobrar`/`TransaccionPago` (lado ventas) — dominios paralelos, no se unifican.
- Sin comprobante adjunto, sin recordatorios de vencimiento, sin notificaciones.
- No se modifica ni avanza la spec `2026-09-08-flujo-caja-backend-design.md` (migración completa de Flujo de Caja a backend).
- El job de generación no reintenta ni notifica si falla una noche puntual; generará la instancia faltante la noche siguiente si sigue dentro del mismo mes (si cruza de mes, esa instancia mensual queda sin generar — aceptable para v1).
