# Permisos extra por usuario — Diseño

## Objetivo

Hoy los permisos de un usuario dependen exclusivamente de su `Rol`
(`SUPER_ADMIN`, `ADMIN`, `VENDEDOR`, `COMPRADOR`, `VISUALIZADOR`), mapeado a
un `Set<Permiso>` fijo en código (`RolPermisos`, ver
`docs/superpowers/specs/2026-08-30-scaffold-desde-slime-erp-old-design.md`,
que dejó esto explícitamente fuera de alcance: *"cualquier modelo de
roles/permisos configurables por tenant... queda fijo en código por
ahora"*). No existe forma de darle a un usuario puntual un permiso que su rol
no incluye (ej: un VENDEDOR con acceso de solo-lectura a Compras).

Este diseño agrega **permisos extra por usuario**: cada usuario conserva su
rol y el set de permisos que ese rol otorga por defecto (sin cambios), pero
un admin puede otorgarle permisos individuales adicionales desde un módulo
nuevo "Roles y permisos".

## Decisiones ya tomadas

- Los permisos extra solo **agregan**, nunca **revocan** — un usuario nunca
  tiene menos permisos que los que le da su rol. Evita el caso confuso de "un
  VENDEDOR sin acceso a Ventas".
- La gestión vive en una **pantalla separada** de "Usuarios" (no se mezcla
  con el formulario de alta/edición de usuario existente), dentro del grupo
  "Administración" del menú.
- Los roles y su mapeo de permisos por defecto (`RolPermisos`) **no
  cambian** — siguen fijos en código. Este diseño es estrictamente aditivo.

## Modelo de datos

Tabla nueva `usuario_permiso`, siguiendo el mismo patrón que el resto de
tablas del proyecto (columna `tenant_id` propia para filtrar directamente sin
depender de un join, `id` autoincremental como PK):

```sql
CREATE TABLE usuario_permiso (
    id             BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id      BIGINT      NOT NULL REFERENCES tenant(id),
    usuario_id     BIGINT      NOT NULL REFERENCES usuario(id),
    permiso        VARCHAR(40) NOT NULL,
    fecha_creacion TIMESTAMP   NOT NULL DEFAULT now(),
    UNIQUE (usuario_id, permiso)
);
```

Migración `V18__usuario_permiso.sql` (siguiente número libre).

Entidad JPA `UsuarioPermiso` en el paquete `cl.slimerp.permisos` (junto a
`Permiso` y `RolPermisos`, que es donde vive hoy el concepto de permisos):
`id`, `tenantId`, `usuarioId`, `permiso` (`@Enumerated(STRING)` sobre
`Permiso`), `fechaCreacion`.

`UsuarioPermisoRepository extends JpaRepository<UsuarioPermiso, Long>` con:
- `List<UsuarioPermiso> findByTenantIdAndUsuarioId(Long tenantId, Long usuarioId)`
- `void deleteByTenantIdAndUsuarioId(Long tenantId, Long usuarioId)` (para
  reemplazar el set completo al guardar)

## Cálculo de permisos efectivos

Hoy `RolPermisos.permisosDe(rol)` se llama en dos lugares que no deben
desincronizarse:

1. `AuthController.login` — arma `LoginResponse.permisos`, que el frontend
   usa para mostrar/ocultar menú y botones (`auth.tienePermiso(...)`).
2. `JwtAuthFilter.doFilterInternal` — arma las `GrantedAuthority` de Spring
   Security en cada request, que son las que realmente hacen cumplir
   `@PreAuthorize("hasAuthority('...')")` en los controladores.

Se centraliza el cálculo en un servicio nuevo:

```java
@Service
public class PermisoEfectivoService {
    private final UsuarioPermisoRepository usuarioPermisoRepository;

    public Set<Permiso> calcular(Long tenantId, Long usuarioId, Rol rol) {
        Set<Permiso> permisos = EnumSet.noneOf(Permiso.class);
        permisos.addAll(RolPermisos.permisosDe(rol));
        usuarioPermisoRepository.findByTenantIdAndUsuarioId(tenantId, usuarioId)
                .forEach(up -> permisos.add(up.getPermiso()));
        return permisos;
    }
}
```

- `AuthController.login` pasa a llamar `permisoEfectivoService.calcular(...)`
  en vez de `RolPermisos.permisosDe(usuario.getRol())` directamente.
- `JwtAuthFilter` recibe `PermisoEfectivoService` por constructor (además de
  `JwtService`, que ya tiene) y lo usa al armar las `authorities`. El JWT ya
  lleva el id del usuario en el claim `sub` (`JwtService.generarToken` hace
  `.subject(usuarioId.toString())`), así que no hace falta cambiar el
  formato del token — solo parsear `claims.getSubject()` como `usuarioId`.

**Costo:** cada request autenticado agrega una consulta a
`usuario_permiso` (antes el cálculo de authorities era 100% en memoria desde
el JWT). Para el volumen actual del sistema esto es aceptable; si más
adelante se vuelve un cuello de botella se puede cachear por
`(tenantId, usuarioId)` con invalidación al guardar cambios — no se
implementa ahora (YAGNI).

## Backend — endpoints nuevos

En `UsuarioController` (mismo controlador que ya gestiona usuarios, mismo
esquema de permisos):

- `GET /api/usuarios/{id}/permisos` — `@PreAuthorize("hasAuthority('USUARIOS_VER')")`.
  Devuelve el rol del usuario, el set de permisos que ese rol otorga por
  defecto, y el set de permisos extra actualmente asignados. Response:

  ```json
  {
    "rol": "VENDEDOR",
    "permisosRol": ["CLIENTES_VER", "CLIENTES_EDITAR", ...],
    "permisosExtra": ["COMPRAS_VER"]
  }
  ```

- `PUT /api/usuarios/{id}/permisos-extra` — `@PreAuthorize("hasAuthority('USUARIOS_EDITAR')")`.
  Body `{ "permisos": ["COMPRAS_VER", "TESORERIA_ANULAR"] }` — **reemplaza**
  el set completo de permisos extra de ese usuario (borra los que ya no
  vienen en la lista, inserta los nuevos). Si el body incluye un permiso que
  el usuario ya tiene por su rol, se ignora silenciosamente al guardar (no
  es un error, pero no genera una fila redundante en `usuario_permiso`) —
  evita que la UI tenga que preocuparse de filtrar antes de enviar.
  Ambos endpoints validan que el usuario pertenezca al tenant actual
  (`usuarioRepository.findByIdAndTenantId`), igual que el resto del
  controlador.

## Frontend

### Modelo y servicio

`Permiso` ya existe como tipo string-enum en `models.ts` (usado por
`auth.tienePermiso`). Se agregan tipos `PermisosUsuario` (`rol`,
`permisosRol: Permiso[]`, `permisosExtra: Permiso[]`) y un método nuevo en
`UsuarioService`:

```ts
obtenerPermisos(id: number): Observable<PermisosUsuario>
guardarPermisosExtra(id: number, permisos: Permiso[]): Observable<void>
```

### Pantalla nueva "Roles y permisos"

Ruta `/usuarios/permisos`, componente `RolesPermisosComponent`, junto a
`UsuariosComponent` en `features/usuarios/`. En el menú lateral (`layout`),
un ítem nuevo dentro del grupo "Administración", junto a "Usuarios",
protegido por `USUARIOS_VER` igual que la pantalla de Usuarios.

Layout (dos secciones, siguiendo la guía de formularios del proyecto:
información principal arriba, detalle/checklist abajo):

1. **Selector de usuario** — buscador o `<select>` con los usuarios del
   tenant (reutiliza `usuarioService.listar()`, ya cargado en la pantalla de
   Usuarios). Al elegir uno, se pide `GET .../permisos`.
2. **Checklist de permisos**, agrupado por módulo (Ventas, Compras,
   Productos, Categorías, Bodegas, Movimientos, Tesorería, Clientes,
   Proveedores, Formas de pago, Usuarios, Empresas — mismo agrupamiento que
   el menú lateral), un checkbox por `Permiso`:
   - Los que están en `permisosRol` aparecen **marcados y deshabilitados**
     (no se pueden desmarcar — vienen del rol).
   - Los que están en `permisosExtra` aparecen marcados y editables.
   - El resto, desmarcados y editables.
3. Botón **Guardar** (`USUARIOS_EDITAR`, mismo criterio que el resto del
   módulo) que junta los checkboxes marcados-y-editables y llama a
   `guardarPermisosExtra`.

Reutiliza los estilos ya existentes de `.form-panel`, `.form-grid`,
`.checkbox-row` (tokens de diseño de la app) — no se crean componentes
visuales nuevos, solo se ensamblan los que ya existen en el sistema de
diseño.

## Fuera de alcance

- Revocar permisos que el rol otorga por defecto (decisión tomada:
  solo-agregar).
- Editar el mapeo `Rol → Permiso` en sí (`RolPermisos` sigue fijo en
  código).
- Roles personalizados / dinámicos.
- Auditoría de cambios de permisos (quién otorgó qué y cuándo) — la tabla
  guarda `fecha_creacion` pero no hay pantalla de historial.
- Caché de permisos efectivos (ver nota de costo arriba).
