# Módulo de Gastos — Design

## Contexto

Hoy no existe ningún registro real de gastos en el sistema. `Compras` (`cl.slimerp.compras`) solo mueve stock — no tiene rastro monetario ni de tesorería. Dentro de `Flujo de Caja` (`frontend/src/app/features/flujo-caja`, ver `docs/superpowers/specs/2026-09-08-flujo-caja-backend-design.md` y `2026-09-10-flujo-caja-cobros-tesoreria-design.md`) existe una sección de "categorías de ingreso y gastos", pero es enteramente client-side (`localStorage`, sin tenant, sin id autoincremental) — no sirve como registro contable real, solo como insumo de proyección personal del usuario.

El usuario necesita un módulo para **registrar gastos reales** (distintos de Compras): arriendo, servicios, sueldos, marketing, etc. Debe quedar persistido en el backend (regla de `CLAUDE.md`: id autoincremental generado por la base de datos, nunca por el frontend) y aparecer automáticamente en Flujo de Caja, siguiendo el mismo patrón de sincronización de solo lectura ya usado para los Cobros de Tesorería (spec `2026-09-10-flujo-caja-cobros-tesoreria-design.md`).

## Decisiones validadas con el usuario

1. **Persistencia**: backend real (tabla propia, id autoincremental, API REST) — no client-side como las categorías actuales de Flujo de Caja.
2. **Categorías de gasto**: tabla propia `categoria_gasto` con CRUD simple (mismo patrón que `catalogo.Categoria`), no un enum fijo en código.
3. **Recurrencia**: sí, con generación automática de filas reales. Un gasto recurrente (ej. arriendo mensual) se define una vez y el backend genera automáticamente un `Gasto` real por periodo, editable/eliminable individualmente sin afectar las instancias futuras.
4. **Campos**: mínimos por ahora — categoría, monto, fecha, descripción (+ recurrencia). Sin proveedor, sin estado de pago, sin comprobante adjunto en esta iteración.
5. **Ubicación**: nueva página **Tesorería > Gastos** (no una pestaña dentro del shell de Flujo de Caja).
6. Los gastos generados se sincronizan a Flujo de Caja como líneas de **solo lectura**, exactamente igual al patrón de `CobrosSyncService`. Los ítems manuales que ya existen hoy en Flujo de Caja (`OneOffItem`/`RecurringItem` con `kind='expense'`) no se tocan ni se reemplazan.
7. **Restricción global de git**: ningún paso de este trabajo — ni al escribir esta spec, ni durante la implementación, ni ningún subagente que se despache para ejecutarla — debe correr comandos git que muten el repositorio (`add`, `commit`, `push`, `merge`, `reset`, creación de ramas, etc.). Comandos de solo lectura (`status`, `diff`, `log`, `show`) sí están permitidos para inspección. El commit se hace únicamente cuando el usuario lo pida explícitamente en el momento.

## Arquitectura

```
Backend (nuevo): cl.slimerp.gastos
  categoria_gasto ← CRUD simple (igual que catalogo.Categoria)
  gasto_recurrente ← plantilla de gasto periódico
  gasto ← registro real (puntual o generado desde gasto_recurrente)
       ↑
  GastoRecurrenteGeneratorJob (@Scheduled, diario) crea filas `gasto`

Frontend (nuevo): frontend/src/app/features/gastos/
  Tesorería > Gastos → CRUD de gastos + categorías + recurrentes

Frontend (flujo-caja, extendido): GastosSyncService
  pagina GastoService.listar() → SyncedExpense[] → projection.ts
  (mismo patrón que CobrosSyncService / SyncedIncome)
```

## 1. Backend — modelo de datos

Migración `V29__gastos.sql`. Todas las tablas `tenant_id BIGINT NOT NULL REFERENCES tenant(id)`, `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, montos `NUMERIC(14,2)`.

```sql
CREATE TABLE categoria_gasto (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    nombre VARCHAR(100) NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT uq_categoria_gasto_tenant_nombre UNIQUE (tenant_id, nombre)
);

CREATE TABLE gasto_recurrente (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    categoria_gasto_id BIGINT NOT NULL REFERENCES categoria_gasto(id),
    monto NUMERIC(14,2) NOT NULL,
    descripcion VARCHAR(255) NOT NULL,
    dia_mes SMALLINT NOT NULL CHECK (dia_mes BETWEEN 1 AND 28),
    fecha_inicio DATE NOT NULL,
    fecha_fin DATE,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now()
);

CREATE TABLE gasto (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL REFERENCES tenant(id),
    categoria_gasto_id BIGINT NOT NULL REFERENCES categoria_gasto(id),
    gasto_recurrente_id BIGINT REFERENCES gasto_recurrente(id),
    monto NUMERIC(14,2) NOT NULL,
    descripcion VARCHAR(255) NOT NULL,
    fecha DATE NOT NULL,
    activo BOOLEAN NOT NULL DEFAULT TRUE,
    fecha_creacion TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX idx_gasto_tenant_fecha ON gasto (tenant_id, fecha);
CREATE INDEX idx_gasto_recurrente_origen ON gasto (gasto_recurrente_id);
```

`dia_mes` se limita a 1-28 para que todo mes (incluido febrero) tenga ese día — evita reglas especiales de fin de mes.

Java, package `cl.slimerp.gastos`: entidades `CategoriaGasto`, `GastoRecurrente`, `Gasto` (mismo estilo Lombok `@Entity`/`@Getter`/`@Setter`/`@Builder` que `Categoria`/`Compra`).

## 2. Backend — servicios y endpoints

- `CategoriaGastoService`/`Controller`/`Repository` — calco de `CategoriaService`/`Controller`/`Repository`: crear, listar paginado con búsqueda por nombre, editar, desactivar. `GET/POST/PUT /api/gastos/categorias`.
- `GastoRecurrenteService`/`Controller`/`Repository` — CRUD de plantillas (crear, listar, editar, desactivar). Desactivar una plantilla no borra ni afecta los `Gasto` ya generados. `GET/POST/PUT /api/gastos/recurrentes`.
- `GastoService`/`Controller`/`Repository` — CRUD de gastos puntuales + listado paginado con filtros (rango de fecha, categoría), igual patrón que `MovimientoInventarioController`/`CompraController`. `GET/POST/PUT/DELETE /api/gastos`.
  - `crear()` valida que `categoriaGastoId` pertenezca al tenant y esté activa.
  - Editar/eliminar un `Gasto` generado por una recurrencia es igual a uno puntual — no valida contra `gasto_recurrente_id` (son instancias independientes una vez creadas).

Todos los servicios usan `TenantContext.getTenantId()` para el scoping, igual que `CompraService`/`CategoriaService`.

### Job de generación automática

`GastoRecurrenteGeneratorJob`, `@Scheduled(cron = "0 0 3 * * *")` (diario, 03:00) — no existe `@Scheduled` en el proyecto hoy, así que se agrega `@EnableScheduling` en `SlimErpApplication`.

Por cada tenant y cada `gasto_recurrente` activo cuyo `dia_mes` sea hoy (y `fecha_inicio <= hoy` y (`fecha_fin` es null o `>= hoy`)):
- Si ya existe un `gasto` con ese `gasto_recurrente_id` cuya `fecha` caiga en el mes actual → no hace nada (idempotencia, cubre reinicios/reintentos del job).
- Si no existe → crea un `Gasto` con `fecha = hoy`, `monto`/`descripcion`/`categoria_gasto_id` copiados de la plantilla, `gasto_recurrente_id` seteado.

## 3. Permisos

`Permiso.java`: agrega `GASTOS_VER`, `GASTOS_EDITAR`. Se agregan a `RolPermisos.java` en los mismos roles que hoy tienen `COMPRAS_VER`/`COMPRAS_EDITAR` (administración/tesorería), a confirmar el detalle exacto de roles al implementar.

## 4. Frontend — `frontend/src/app/features/gastos/`

- `gastos.component.ts`/`.html` — pantalla principal, mismo esqueleto que `CategoriasComponent`/`ComprasComponent`: tabla paginada (`MatTableModule`+`MatPaginatorModule`) con filtro por categoría y rango de fecha (`Subject` + `debounceTime(300)`), formulario inline de alta/edición (`NgForm` template-driven), `mostrarCargando()`/`cerrarCargando()`, `MonedaPipe` para montos.
- `gastos-recurrentes.component.ts`/`.html` — pantalla/pestaña secundaria con el CRUD de plantillas recurrentes (categoría, monto, descripción, día del mes, fecha inicio/fin, activo).
- Categorías de gasto: panel o diálogo simple dentro de la misma pantalla de Gastos (lista + form), igual a cómo `CategoriasComponent` maneja Categoría/Subcategoría de producto lado a lado — no una ruta aparte.
- Formularios siguiendo la guía de `CLAUDE.md`: secciones (datos del gasto → categoría/recurrencia → acciones), 1-2 columnas, validación junto al campo, botón primario diferenciado, responsive.
- Nav: entrada **Tesorería > Gastos** en `layout.component.ts`, ruta `/gastos` en `app.routes.ts`, gateada por `GASTOS_VER`/`GASTOS_EDITAR`.

## 5. Sincronización a Flujo de Caja

Réplica exacta del patrón de `CobrosSyncService` (`2026-09-10-flujo-caja-cobros-tesoreria-design.md`), sin cambios de backend adicionales — solo consume `GET /api/gastos`:

- `frontend/.../flujo-caja/core/gastos-sync.service.ts` (nuevo): pagina `GastoService.listar({ activo: true, pagina, tamano: 200 })` hasta traer todo, mapea cada `Gasto` con una función pura `mapGastoToSyncedExpense`.
- `frontend/.../flujo-caja/core/synced-expense.ts` (nuevo):
  ```ts
  export interface SyncedExpense {
    id: string;              // `gasto-${gasto.id}`
    month: MonthKey;         // gasto.fecha.slice(0,7)
    description: string;     // `${gasto.categoriaGastoNombre}: ${gasto.descripcion}`
    amount: number;
    gastoId: number;         // para el link "Ver gasto"
  }
  ```
- `core/projection.ts`: `Line['source']` ya tiene `'synced'` (de la spec de Cobros); se reutiliza. `projectMonth`/`projectMonths`/`projectThrough`/`projectYear` ganan un parámetro adicional `syncedExpenses: readonly SyncedExpense[] = []`, con un loop análogo al de `syncedIncomes` pero `kind: 'expense'`. A diferencia de los cobros (que usan `CATEGORIA_VENTAS_ID`), las líneas de gasto sincronizado **no se mapean a una `Category` cliente de Flujo de Caja** — se muestra el nombre de la categoría de gasto directamente en la descripción, evitando duplicar/mapear entre dos fuentes de verdad de categorías distintas. `Line` gana `gastoId?: number` opcional (paralelo a `cuentaPorCobrarId`).
- `core/cashflow.store.ts`: nueva señal `_syncedExpenses`, nuevo método `syncGastos()` (mismo manejo de `syncing`/`syncError`/403 que `syncCobros()`), llamado también en el constructor. `projection` computed pasa ambos, `syncedIncomes` y `syncedExpenses`, a `projectYear`.
- `month/month-detail.html`: la rama que hoy distingue `'synced'` (ingresos) se extiende para gastos sincronizados — mismo ícono `sync`/tooltip, sin editar/eliminar, con link "Ver gasto" hacia `/gastos?id={{ line.gastoId }}` (o equivalente) en vez de "Ver cuenta".

## Fuera de alcance

- Proveedor, estado de pago (pagado/pendiente), forma de pago y comprobante adjunto en el gasto — quedan para una iteración futura si se pide.
- Compras sigue sin generar movimiento de caja/gasto automático — no se cruza con este módulo.
- No se modifica ni avanza la spec `2026-09-08-flujo-caja-backend-design.md` (migración completa de Flujo de Caja a backend).
- No hay deduplicación entre un gasto sincronizado y un ítem manual (`OneOffItem`/`RecurringItem`) que el usuario ya haya cargado a mano en Flujo de Caja para el mismo concepto — igual que ya ocurre con los cobros.
- El job de generación no reintenta ni notifica si falla una noche puntual; simplemente generará la instancia faltante la noche siguiente si sigue dentro del mismo mes (si cruza de mes, esa instancia mensual quedaría sin generar — aceptable para v1, revisar si se vuelve un problema real).

## Testing

- `GastoRecurrenteGeneratorJobTest` (backend): genera la instancia correcta la primera vez, no duplica en una segunda ejecución el mismo día/mes, no genera si `fecha_fin` ya pasó o `fecha_inicio` es futura.
- Tests de servicio para `GastoService`/`CategoriaGastoService`/`GastoRecurrenteService` (scoping por tenant, validaciones), siguiendo el estilo de tests ya existentes para `CompraService`/`CategoriaService`.
- `projection.spec.ts` (frontend, ya existe desde la spec de Cobros): nuevos casos para la rama `synced`/`expense` — un gasto sincronizado cae en el mes correcto, se resta del total, no requiere una `Category` de Flujo de Caja para clasificarse.
- `gastos-sync.service.spec.ts`: test de la función pura `mapGastoToSyncedExpense`.
- Verificación manual: crear una categoría de gasto, un gasto puntual y un gasto recurrente en Tesorería > Gastos; confirmar que ambos aparecen en Flujo de Caja del mes correcto, solo lectura, con link de vuelta; confirmar que tras correr el job (o simular el día) se genera automáticamente la siguiente instancia del recurrente.
